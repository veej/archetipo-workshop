## User Story

**Epic:** EP-002 — Partecipanti e Inviti
**Priorità:** HIGH | **Story Points:** 3

**Story**
Come Sara (Partecipante), voglio cliccare il link di invito, autenticarmi con Google in un click ed essere immediatamente dentro il viaggio, così da accedere a tutte le informazioni senza un onboarding complicato.

**Criteri di Accettazione**
- [ ] Seguendo il link di invito, l'utente non autenticato viene reindirizzato alla pagina di sign-in con il token preservato nel redirect
- [ ] Dopo il login OAuth, l'utente è automaticamente aggiunto come partecipante del viaggio corrispondente al token
- [ ] L'utente viene reindirizzato alla dashboard del viaggio (`/trips/[id]`) dopo l'accettazione
- [ ] Un token già usato o scaduto mostra una pagina di errore con messaggio esplicativo e link al sign-in
- [ ] Il viaggio appare immediatamente nella lista viaggi dell'utente dopo l'accettazione

## Soluzione Tecnica

La soluzione sfrutta il parametro `?next` già gestito dal callback OAuth esistente, aggiungendo una route Server Component pura `/invite/[token]` che esegue validazione, join e redirect interamente lato server senza roundtrip client.

- **Modifica `src/app/auth/signin/page.tsx`**: leggere `?next` da `window.location.search` al momento del click OAuth (non al render, per evitare il Suspense boundary richiesto da `useSearchParams()`), iniettarlo nel `redirectTo` come `${window.location.origin}/auth/callback?next=${encodeURIComponent(next)}`. Il callback esistente legge già `searchParams.get("next") ?? "/dashboard"` — nessuna modifica al callback necessaria.
- **Server action `joinTripByInvite(token)` in `src/app/actions/invites.ts`**: auth via `getCurrentUser()`, lookup `TripInvite` con `{ where: { token }, include: { trip: true } }` e check `expiresAt > new Date()`, verifica idempotenza con `TripParticipant.findUnique({ where: { tripId_userId } })` — se già partecipante (qualsiasi ruolo) restituisce `{ success: true, tripId }` senza alterare il ruolo esistente, altrimenti crea `TripParticipant` con `role: PARTICIPANT, status: ACTIVE` e revalida `/dashboard` e `/trips/[tripId]`.
- **Route `src/app/invite/[token]/page.tsx`** — Server Component: valida il token con Prisma, se scaduto/non trovato renderizza `<InviteError reason="expired|invalid">`, se utente non autenticato esegue `redirect('/auth/signin?next=/invite/${token}')`, se autenticato chiama `joinTripByInvite(token)` ed esegue `redirect('/trips/${tripId}')`.
- **Componente `src/app/invite/[token]/invite-error.tsx`**: Client Component separato con i due stati di errore (scaduto / non valido), messaggio esplicativo e CTA verso la sign-in page — estratto per permettere i render test con Testing Library.
- **Middleware e schema Prisma**: nessuna modifica — `/invite/*` non è nella lista protetta del middleware; `TripInvite` e `TripParticipant` esistono già nello schema.

## Strategia di Test

La priorità è verificare l'idempotenza del join (silenziosamente sbagliata se non testata) e il corretto filtraggio dei token scaduti — i due rischi con il minor segnale di errore visibile in produzione.

- **Unit test `joinTripByInvite`**: utente non autenticato → errore; token scaduto → errore; token valido + utente nuovo → `TripParticipant` creato con `role: PARTICIPANT`; token valido + utente già partecipante (PARTICIPANT o ORGANIZER) → restituisce `{ success: true, tripId }` senza creare duplicati né modificare il ruolo.
- **Render test `<InviteError>`**: Testing Library — `reason="expired"` mostra "Link scaduto" + CTA sign-in; `reason="invalid"` mostra "Link non valido" + CTA sign-in.
- **Integration test join e scadenza**: `TripInvite` con `expiresAt` nel passato → join rifiutato; `TripInvite` con `expiresAt` nel futuro → `TripParticipant` creato; secondo join con stesso utente → nessun record duplicato, `TripParticipant.count` resta 1.
