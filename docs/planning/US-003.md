## User Story

**Epic:** EP-001 — Gestione Viaggi
**Priorità:** HIGH | **Story Points:** 5

**Story**
Come Sara (Partecipante), voglio aprire un viaggio e vedere immediatamente le tappe di oggi, i documenti più recenti e il mio saldo personale, così da sapere in 10 secondi dove dormo, a che ora è il volo e quanto devo al gruppo.

**Criteri di Accettazione**
- [ ] La sezione "Oggi" mostra le tappe dell'itinerario del giorno corrente (empty state con messaggio se nessuna tappa è programmata per oggi)
- [ ] La sezione "Documenti recenti" mostra gli ultimi 3 documenti caricati nel viaggio (empty state se nessun documento presente)
- [ ] La sezione "Il mio saldo" mostra il saldo netto dell'utente corrente verso il gruppo (mostra "0 €" se nessuna spesa registrata)
- [ ] Solo i partecipanti autenticati del viaggio possono accedere alla dashboard; altri utenti ricevono errore 403
- [ ] La dashboard è accessibile all'URL `/trips/[id]` e include link di navigazione alle sezioni itinerario, documenti e spese

## Soluzione Tecnica

La dashboard è un Server Component che aggrega dati da tre domini (itinerario, documenti, spese) in un'unica chiamata helper, con estensione minima dello schema Prisma per anticipare i modelli che EP-003/004/005 utilizzeranno a pieno — evitando migrazioni schema ridondanti in ogni storia futura.

- **Schema Prisma: 4 nuovi modelli** — `ItineraryStop` (tripId, name, date, time?, address?, notes?), `Document` (tripId, name, fileKey, `DocumentCategory` enum, uploadedBy FK→User), `Expense` (tripId, description, amount, date, paidById FK→User), `ExpenseParticipant` (expenseId, userId, amount). Relazioni inverse aggiunte a `Trip` e `User`. Eseguire `npx prisma db push && npx prisma generate` dopo la modifica.
- **`getTripDashboard(tripId, userId)` in `src/lib/trips.ts`** — funzione server-side con 4 query Prisma: (1) verifica `TripParticipant` ACTIVE (restituisce `null` se assente o trip inesistente), (2) tappe odierne con `where: { tripId, date: { gte: startOfDay, lt: endOfDay } }`, (3) ultimi 3 documenti con `orderBy: { createdAt: 'desc' }, take: 3`, (4) saldo netto calcolato come `SUM(Expense.amount WHERE paidById=userId) - SUM(ExpenseParticipant.amount WHERE userId=userId)`. Il confronto date usa UTC lato server — approssimazione accettabile per l'MVP.
- **`/trips/[id]/page.tsx`** — Server Component: chiama `getCurrentUser()` + redirect se non autenticato, poi `getTripDashboard(params.id, user.id)` + pagina 403 inline se restituisce `null`, altrimenti renderizza `TripDashboard` con dati.
- **`src/components/trips/trip-dashboard.tsx`** — Client Component: header viaggio (nome, destinazione, date, cover via `TripCover`), barra di navigazione con `Link` verso `/trips/[id]/itinerary`, `/trips/[id]/documents`, `/trips/[id]/expenses`, `/trips/[id]/participants`; tre sezioni "Oggi" / "Documenti recenti" / "Il mio saldo" con empty state dedicato per ciascuna.
- **Middleware** — Verificare e aggiornare `src/middleware.ts` per proteggere `/trips/:path*` se non già fatto da US-002.

## Strategia di Test

La strategia prioritizza la correttezza della logica di saldo (unica matematica non triviale) e l'accesso controllato ai dati del viaggio — i due rischi maggiori di questa storia.

- **Unit test formula saldo:** Vitest — nessuna spesa → 0, utente solo pagante → positivo, utente solo debitore → negativo, mix pagante+debitore → differenza corretta.
- **Integration test `getTripDashboard`:** non-partecipante → `null`; trip inesistente → `null`; viaggio senza dati → tappe `[]`, documenti `[]`, saldo `0`; viaggio con dati → conteggi e aggregati corretti.
- **Render test `TripDashboard`:** Testing Library — sezione "Il mio saldo" con saldo positivo mostra indicatore verde; con saldo negativo mostra indicatore rosso; empty state visibili quando array vuoti.
- **E2E accesso:** utente non autenticato → redirect a `/auth/signin`; utente autenticato non partecipante → pagina 403; partecipante → dashboard visibile con sezioni corrette.
