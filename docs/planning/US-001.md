## User Story

**Epic:** EP-001 — Gestione Viaggi
**Priorità:** HIGH | **Story Points:** 3

**Story**
Come Marco (Coordinatore), voglio creare un nuovo viaggio specificando nome, date di inizio/fine, destinazione principale e un'immagine di copertina opzionale, così da poter configurare l'hub condiviso per il mio gruppo in pochi minuti.

**Criteri di Accettazione**
- [ ] L'utente autenticato può creare un viaggio con nome, data inizio, data fine e destinazione principale (tutti obbligatori)
- [ ] Il campo immagine di copertina è opzionale; se non fornita, viene mostrato un placeholder visivo
- [ ] Il viaggio creato compare nella lista viaggi dell'utente immediatamente dopo la creazione
- [ ] L'utente creatore è automaticamente impostato come organizzatore del viaggio (ruolo ORGANIZER)
- [ ] Tentare di creare un viaggio con data fine antecedente alla data inizio mostra un errore inline

## Soluzione Tecnica

Approccio schema-first con Server Action e modal client-side: si parte dall'estensione del Prisma schema come fondamenta condivise per tutto il prodotto, poi si implementa una Server Action che gestisce creazione e validazione atomicamente, e infine si aggiorna il dashboard con un modal che la invoca.

- **Prisma schema:** aggiungere `Trip` (id UUID, name, startDate, endDate, destination, coverKey nullable, createdAt, updatedAt), `TripParticipant` (id UUID, tripId, userId, role, status, createdAt) e gli enum `TripRole` (ORGANIZER/PARTICIPANT) e `ParticipantStatus` (ACTIVE/DEACTIVATED) con relazioni bidirezionali verso `User`. Questi modelli sono prerequisiti fondazionali per US-002–US-018.
- **Server Action `createTrip`** in `src/app/actions/trips.ts`: riceve `FormData`, valida lato server (campi obbligatori + `endDate >= startDate`), crea Trip e TripParticipant in un `prisma.$transaction()` per atomicità, invoca `revalidatePath("/dashboard")` a successo. Restituisce errori per campo in caso di validazione fallita.
- **Client Component `CreateTripModal`** in `src/components/trips/create-trip-modal.tsx`: Dialog shadcn con form (nome, date, destinazione, selettore cover preset con illustrazioni). Usa `useActionState` (React 19 / Next.js 15) per invocare la Server Action e mostrare errori inline per campo. Si chiude automaticamente a successo.
- **Aggiornamento `/dashboard`**: server component che fetcha i viaggi dell'utente via `prisma.tripParticipant.findMany({ where: { userId, status: "ACTIVE" }, include: { trip: true } })` e renderizza trip card + trigger del modal. Gestisce l'empty state con CTA per creare il primo viaggio. Soddisfa AC3 senza anticipare la UI completa di US-002.
- **Cover image:** campo `coverKey` nullable che accetta una chiave di illustrazione preset (es. `"tokyo"`, `"paris"`). Nessun file upload — rimandato a funzionalità post-MVP.

## Strategia di Test

La strategia copre l'intera piramide: unit test sulla logica di validazione, test di integrazione sulla persistenza atomica, e test e2e sul comportamento visibile all'utente — quest'ultimo è il più critico per verificare AC3 (lista immediata dopo creazione).

- **Unit test `createTrip` action:** verifica errori per ogni campo obbligatorio mancante, rifiuto di date invertite, rifiuto di date con fine < inizio. Framework: Vitest con mock di Prisma.
- **Integration test:** verifica che dopo `createTrip` con dati validi esistano nel DB sia il record `Trip` che il `TripParticipant` con `role: ORGANIZER` e `userId` dell'utente corrente. Test contro DB di test o Prisma mock con client reale.
- **E2E test dashboard:** (1) creazione viaggio valido → trip card appare in lista; (2) data fine < data inizio → errore inline visibile, form non submittato; (3) tutti i campi obbligatori vuoti → errori per campo; (4) utente non autenticato su `/dashboard` → redirect a `/auth/signin`.
