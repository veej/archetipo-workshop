## User Story

**Epic:** EP-003 — Itinerario Giornaliero
**Priorità:** HIGH | **Story Points:** 3

**Story**
Come Marco (Coordinatore), voglio aggiungere una tappa all'itinerario specificando nome, giorno, orario, indirizzo e note opzionali, così che tutti i partecipanti possano vedere il piano strutturato giorno per giorno.

**Criteri di Accettazione**
- [ ] Solo gli organizzatori possono aggiungere tappe all'itinerario
- [ ] Una tappa include: nome (obbligatorio), giorno (obbligatorio, selezionabile tra le date del viaggio), orario (opzionale), indirizzo (opzionale), note libere (opzionale)
- [ ] La tappa salvata compare immediatamente nella vista itinerario nella giornata corrispondente
- [ ] Tentare di salvare una tappa senza nome o senza giorno mostra errori inline prima della submission

## Soluzione Tecnica

Il modello `ItineraryStop` è già definito nello schema Prisma con tutti i campi necessari; l'implementazione segue gli stessi pattern delle sezioni esistenti (lib function → server action → server component page → client component), senza migrazioni DB.

- **`src/lib/itinerary.ts`** — `getItineraryStops(tripId, userId)`: verifica partecipazione attiva (stesso pattern di `getTripDashboard`), carica tutte le `ItineraryStop` del viaggio ordinate per `date asc, time asc`, restituisce `{ stops, role, trip }` o `null` se non autorizzato
- **`src/app/actions/itinerary.ts`** — `addItineraryStop(tripId, formData)` con `"use server"`: auth check Supabase, role check `ORGANIZER` su `TripParticipant`, validazione `name` e `date` obbligatori, `prisma.itineraryStop.create`, `revalidatePath` sulla pagina itinerary
- **`src/app/trips/[id]/itinerary/page.tsx`** — server component: auth check → redirect, `getItineraryStops` → `forbidden()` se null, passa dati al client component
- **`src/components/trips/itinerary-tab.tsx`** — client component con trip hero + nav tab ("Itinerario" attivo), tappe raggruppate per giorno (array → `Map<dateString, stops[]>`), empty state per giorni senza tappe, pulsante "Aggiungi tappa" visibile solo a `ORGANIZER`
- **`src/components/trips/add-stop-modal.tsx`** — `Dialog` shadcn/ui con form: `name` (required), `date` (type="date", vincolato a `trip.startDate`–`trip.endDate`), `time` (optional), `address` (optional), `notes` (textarea optional); `useActionState` per errori inline, toast via sonner su successo
- Il `tripId` viene passato alla server action tramite `bind` (non hidden input) per evitare tampering

## Strategia di Test

La strategia copre tre livelli: unit test sulla action (incluso il check di ruolo lato server, che è il controllo di sicurezza più critico), integration test sulla lib function per verificare l'autorizzazione e l'ordinamento, e component test sul modal per validare il comportamento della form lato client.

- **Unit test `addItineraryStop`** (unit): utente non autenticato, partecipante non-organizzatore, name mancante, date mancante, successo con `revalidatePath` chiamato
- **Integration test `getItineraryStops`** (integration): utente non partecipante → null, partecipante DEACTIVATED → null, nessuna tappa → lista vuota, tappe restituite in ordine data + orario
- **Component test `AddStopModal`** (unit/component): errori inline per name/date mancanti, submit con dati validi invoca la action, campi opzionali non bloccano il submit
